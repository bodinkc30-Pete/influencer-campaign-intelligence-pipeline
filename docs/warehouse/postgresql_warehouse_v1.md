# PostgreSQL Warehouse v1

## Goal

Move the governed canonical CSV layers into a persistent PostgreSQL warehouse without changing the source-of-truth semantics.

This phase is a controlled portfolio PostgreSQL implementation. Local runtime evidence has been captured for migration, load, reconciliation, idempotent replay, query planning, run-ledger state, and same-batch skip behavior. It must not be presented as production experience.

## Schemas

- `stg` — load-ready CSV landing tables; text-first so source anomalies are preserved.
- `core` — typed dimensions, facts, constraints, foreign keys and indexes.
- `ops` — pipeline run, incremental state and data-quality results.
- `mart` — analytical views built from governed core tables.

## Core grain

| Table | Grain / business key |
|---|---|
| `core.dim_influencer` | one Golden Master influencer (`influencer_id`) |
| `core.influencer_identity_alias` | one source alias observation (`source_row_hash + alias_type + alias_value`) |
| `core.dim_brand` | one canonical brand (`brand_id`) |
| `core.dim_campaign` | one technical campaign/source instance (`campaign_id`) |
| `core.campaign_requirement` | one governed requirement row per campaign (`campaign_id`) |
| `core.fact_campaign_influencer` | one influencer × campaign (`campaign_id + influencer_id`) |
| `core.fact_campaign_deliverable` | one canonical deliverable (`deliverable_id`) |
| `core.fact_influencer_performance` | one governed influencer performance observation (`performance_id`) |
| `core.fact_campaign_performance` | one governed campaign-level performance observation (`campaign_performance_id`) |

## Incremental / idempotency strategy

1. Canonical files are transformed to load-ready CSVs.
2. CSVs are loaded into `stg` tables.
3. One database transaction performs typed `INSERT ... ON CONFLICT DO UPDATE` operations in dependency order.
4. `fact_campaign_influencer` uses `(campaign_id, influencer_id)` as the business-key conflict target.
5. Other facts use deterministic source IDs generated by prior governed layers.
6. A repeated batch must update the same records rather than append duplicates.
7. `ops.pipeline_run` and `ops.incremental_state` capture run state separately from business data.
8. A SHA-256 manifest fingerprint identifies the nine-file input batch.
9. A batch equal to the last successful fingerprint is recorded as `SKIPPED / SAME_BATCH_GATE` and does not execute staging COPY or core UPSERT.
10. An identical UPSERT preserves `loaded_at` rather than creating timestamp-only drift.

## Date handling

Source date columns are not assumed to be clean. The staging export retains both:

- parsed ISO date column (blank when not safe to parse), and
- original raw text column.

PostgreSQL therefore does not silently turn strings such as Thai date labels or product text into dates.

## Operational runtime gate

The controlled local lab has captured evidence for:

- PostgreSQL version / connection;
- migrations 001–006;
- atomic staging COPY and staging reconciliation;
- core UPSERT and referential reconciliation;
- identical replay with stable row counts and full-row fingerprints;
- mart grain and join-fanout reconciliation;
- representative `EXPLAIN (ANALYZE, BUFFERS)` / index evidence;
- `ops.pipeline_run` lifecycle and DQ evidence;
- `ops.incremental_state` advancement after SUCCESS only;
- same-batch `SKIPPED` behavior without state advancement.

A database-level injected rollback/failure experiment remains an explicit later reliability extension. Do not imply production database operations from this portfolio lab.
